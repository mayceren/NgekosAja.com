# Business data flows

1. **Discovery:** anonymous catalogue RPC → safe listing projection → filters/sort/range → detail/gallery/related choices. Draft/archived rows stay out. Favorites/recent searches require identity and write own rows. Compare stores only public listing UUIDs in the hash URL, at most three.
2. **Contact:** published listing → `open_conversation` derives owner/member identities → member directory → messages via `send_message`. Browser never supplies sender ID. Manual refresh reads replies and unread counts; mark-read updates the existing member cursor through RPC.
3. **Placement:** owner chooses a legitimate property conversation and available room → server derives prospect ID → stores seven-day offer with snapshots → named tenant reviews and responds → owner consumes matching accepted offer through atomic check-in → existing tenant identity, role grant and agreement remain related. Rejected, expired, reused or mismatched terms fail.
4. **Property operations:** form → one property/room RPC → constraints and owner checks → child/header transaction → invalidation → marketplace availability refreshes from operational rooms and active agreements. Delete with history fails; archive retains records.
5. **Billing:** authorized owner selects active agreement → invoice RPC snapshots tenant/property/room and nominal → tenant reads own `invoice_statuses` → detail adds fixed Rp2.000. Bulk commits atomically; recurring generator is manual and deduplicated. Closing a lease stops its recurring schedule.
6. **Payment:** Connected checkout reads invoice/fee/status. Gateway is unavailable; no browser ledger mutation is exposed. A future verified server gateway will call the existing idempotent server RPC. Demo success/failure remains isolated. Printed receipts require a succeeded transaction already present; simulation records are labelled.
7. **Maintenance:** tenant creates actual ticket → timeline/notifications via database triggers → owner transitions and notes/ETA → tenant confirms or reopens → same server rows appear after refresh. Accepted rule recommendations are stored in complaint_analyses; similar complaints are scoped by RLS, never the demo store.
8. **Reporting:** owner/platform reporting functions → actual aggregate values and monthly chart → authorized CSV. GMV, owner rent, admin fees and boost revenue remain distinct. Failed payments never become revenue.
9. **Notifications/settings:** own rows only; manual reminders are deduplicated database operations. Preferences persist to user_settings; session cache clears on relevant identity changes. Realtime/cron/email are not claimed.

Writes are followed by a fresh route fetch. A different browser/account must refresh to observe changes; there is no realtime subscription in Phase 3.
